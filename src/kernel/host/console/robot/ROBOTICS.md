# 机器人操作系统：目标、实现方式与支撑能力

## 零、文档口径

这份文档把原来的目标和现在的路线合并到一起，**不是替换**：

- **总目标**：把 Aevum 做成面向机器人的操作系统内核——让机器人成为内核里的第一类对象，像进程一样被创建、调度、隔离、观测和回收。
- **当前阶段**：先把核心控制内核做扎实，把采样、控制计算、执行器输出收进同一个内核，让控制周期可测、可复现、可降级。
- **实现方式**：机器人核心控制内核 + 原生 3D 世界渲染引擎 + 桌面实时控制测试台。
- **优势**：相比“Linux + ROS 2 + 运动控制卡”的多层栈，少中间件、少拷贝、少排队；建模、控制、观察、验证能在同一条桌面闭环里完成。

原来的说法没有错，继续有效。这里要纠正一个自我设限：**“核心控制内核组件”是当前交付形态和入手点，不是定位的天花板**。

“机器人操作系统”目前没有公认定义，这反而是机会。通用 OS 管的是“上面运行程序”：进程、内存、文件、权限、调度、隔离。机器人 OS 管的是“上面运行机器人”：多机械并行控制、每台机械的上下文与资源、控制任务的时间基准、故障隔离与安全降级。**当内核能同时调度多台机器人、并保证它们互不拖死时，它就已经是操作系统，不是“某个控制组件”了。**

统一后的定位可以写成一句：

> Aevum 是面向机器人的操作系统内核。当前先交付核心控制内核：直接接管传感器和执行器，把“要做什么动作”变成“执行器什么时候、以什么量动”；下一步把多机器人并行控制、资源隔离和故障隔离做成 OS 级能力。3D 世界引擎和桌面测试台负责建模、观察和验证，不进入实时伺服环。

## 一、目标、方式与优势

### 1. 总目标

- 机器人成为内核里的第一类对象：每台机械有独立上下文、资源账、控制任务和故障状态；
- 控制核心路径直接进内核：采样、控制计算、执行器输出在同一套时间基准和地址空间里完成；
- 控制周期、抖动、deadline、CPU 占用和资源水位都可测量；
- 超载时按优先级降级，而不是失控；
- 同一套控制语义能在桌面测试台和真实控制板上重复使用。

在这些目标下，当前实现约束仍然是：

- 单核、无 FPU、无堆、固定内存；
- 用 Q16.16 定点运算代替浮点；
- 用任务调度把伺服、规划、监控放在同一颗 CPU 上；
- 用约束控制和奇异值感知代替高刚度、高成本的专用控制器。

这条路线成立的前提仍然是：控制周期可测、任务可让出、资源占用可观测。

### 2. 实现方式：三件套

1. **机器人核心控制内核组件**：控制环、硬件访问、时间基准、任务隔离，直接控制执行器。
2. **原生 3D 世界渲染引擎**：渲染、建模、场景编辑；机器人/机械臂先在电脑里被搭出来、看清楚。
3. **桌面实时控制测试台**：在电脑上跑同一套控制逻辑，实时看到 3D 机器人怎么动，再烧录到控制板。

### 3. 优势

这三件合起来，才是“为什么不是 Linux + ROS 2 + 运动控制卡”的答案：

- 控制路径没有应用层→中间件→驱动→总线的多次拷贝和排队；
- 3D 引擎不是控制路径里的中间件，它负责建模、渲染、遥测和测试，不参与实时伺服环；
- 模型、控制参数、实时预览和烧录不脱节，不是四个工具各演各的。

## 二、当前机器人学基线

控制算法基线仍是 3R 平面臂：

- 默认 `body.n = 3`，杆长 0.30 / 0.30 / 0.20 m；
- `arm_fk`、`arm_jacobian`、`arm_solve` 是纯函数；
- `arm_control_step` 使用阻尼最小二乘、零空间投影、2×2 闭式奇异值；
- 目标点按三角波沿半径来回扫，最外端故意超出可达半径；
- 面板显示 `w_manip`、`sigma_min/sigma_max`、`err_mm`、`limit_margin`、`null_share`；
- `limit_margin` 目前只统计、不强制，关节位置/速度限幅还没有闭环。

在这个基线之上，代码已经往前走了几步，但还没有改变“单控制上下文”的事实：

- 身体描述支持 3–8 关节，`body.n` 可在运行时由串口/Forge 下发；
- Forge 3D 工作台可以通过串口桥显示真实关节状态、下发手动目标；
- 内核有 V/C/G/K/X/S/Y/T/F/B 等观测与演示页面，能看见任务、地址空间、信号、FPU、池和调度状态；
- `arm_control` 仍是全局单例：一份 `body`、一份 `q/q_target`、一个 `mode`、一个 `control` 任务，没有 robot id，也没有 per-robot 上下文。

所以它已经回答了“怎么算”，也回答了一部分“怎么看见”；还没有回答“多个机械怎么同时控制”，以及“控制核心怎么和 3D 世界、桌面测试台形成同一条闭环”。

## 三、G1（原目标，继续保留）：资源感知的 3R 平面臂约束轨迹跟踪

不直接上 6R 空间臂。先把 3R 平面臂从“追踪一个来回扫的点”升级为“跟踪一条受约束的轨迹”，并把资源账算清楚。

### 1. 轨迹层

- 任务空间轨迹：直线、圆弧、五次多项式/S 曲线；
- 速度、加速度、加加速度（jerk）都有上限；
- 目标不再瞬间跳变，轨迹层每周期给出 `x_d, dx_d, ddx_d`；
- 终点可停留，支持“点到点”和“连续经过”两种模式。

### 2. 约束层

- 关节位置、速度、加速度硬限幅，超限不是显示而是截断/投影；
- 奇异值自适应阻尼：`sigma_min` 低于阈值时提高 `lambda`，离开后恢复；
- 零空间姿态优先级：限位或奇异时先保末端，再回 `q_pref`；
- 输出限幅后的 `dq` 和实际可达的 `dx`，让上层知道“指令被改了多少”。

### 3. 调度层

在进程管理补上 PIT/IDT 后，把控制拆成三个任务：

- `servo`：固定周期（先 200 Hz，稳定后再冲 1 kHz），只做一步控制；
- `planner`：较低频率，算轨迹和约束投影；
- `monitor`：最低优先级，统计误差、限幅次数、奇异值、deadline miss。

调度器要给出每个任务的：

- 周期、实际开始/结束时刻、抖动；
- deadline miss 次数；
- CPU 占用（用切换计数或时间戳近似）。

资源紧张时按优先级降级：先停 `monitor`，再降 `planner` 频率，最后才让 `servo` 掉周期。

### 4. 验收指标

- 关节位置/速度/加速度越限次数为 0；
- 末端跟踪 RMS 误差小于 5 mm（仿真口径）；
- 最大关节速度不超过 3.00 rad/s；
- `sigma_min` 不低于当前基线的最差值；
- 稳态 deadline miss 小于 1%；
- QEMU 只做功能验收；抖动和 1 kHz 周期必须在真实机器上测，不能拿 TCG 当实时证据。

### 5. 演示页要求

G1 的每个可见能力都要落到页面上，例如：

- 轨迹类型、当前 `x_d/dx_d/ddx_d`；
- 限幅前后的 `dq`、限幅次数；
- `sigma_min`、自适应 `lambda`；
- deadline miss、控制周期抖动、任务 CPU 占用。

没有页面的 G1 子功能，不按完成处理。

## 四、G2（OS 级能力）：多智能机械并行控制

这是当前最明确的架构缺口，也是 Aevum 从“单机械控制内核”走向“机器人操作系统”的分界线。要解决“内核不能同时操控几个智能机械”，先把拓扑说清楚，再做上下文。

### 1. 先定拓扑

- 同一块控制板带多条臂；
- 多块控制板组网，每块板控制一台机械；
- 或者“主控内核 + 分布式执行节点”。

拓扑不同，`robot_id` 的位置和总线协议不同，不能先写代码再猜。

### 2. 控制上下文

把现在 `arm_control` 里的单例状态拆成 per-robot 上下文：

- `robot_id` / namespace；
- 每台机械独立的 `body`、`q`、`q_target`、`mode`、`manual_deadline`；
- 每台机械独立的控制任务，或单控制任务轮询多个上下文；
- 每台机械独立的状态帧、错误状态、限幅计数和安全停止。

### 3. 总线与路由

- UART/CAN/EtherCAT 命令要带 robot id / joint id；
- 状态帧按 robot id 路由，不能靠“最后一条连接”猜对象；
- 断线、超时、过载只降级对应机械，不拖死其它机械。

### 4. 演示页要求

至少有一个多机械页面：

- 两台机械的 `q/q_target/mode/err_mm` 同时显示；
- 单独下发目标时，只影响对应机械；
- 一台进入 BLOCKED/FAULT/断线，另一台继续运行；
- 页面能明确显示当前控制的是哪一台。

### 5. 验收判据

- 两台机械独立目标、独立状态、独立超时；
- 一台故障不影响另一台的伺服周期；
- 页面和串口都能看出“命令发给了谁”。

## 五、G3（支撑能力）：原生 3D 世界与 Forge 工作台

3D 引擎的定位不是“好看的 demo”，而是机器人控制组件的原生建模与验证环境。

### 1. 已有资产

- `engine/` 是独立 WebGL2 角色/世界渲染引擎，能渲染 PMX/MMD、VRM/glTF、Live2D、地形、天气、水体、植被、LOD；
- `interface/web/forge/` 是 3D 机器人工作台：结构树、3D 视口、Inspector、glTF/GLB 导入、关节编辑、手动控制、内核状态面板；
- 内核通过串口桥回传关节状态，Forge 显示真实 q 曲线；这条链路已经跑通过。

### 2. 要补的闭环

- 模型：导入/搭建机械臂，关节轴、杆长、限位和身体描述能落到同一份配置；
- 控制：Forge 下发目标，内核进入 MANUAL，状态帧回传真实 `q`；
- 观察：3D 视口和内核 VGA 面板显示同一组状态；
- 验证：桌面测试台先跑通，再把同一套控制语义烧到控制板。

### 3. 边界

- 3D 引擎可以下发目标、显示状态、做测试；
- 3D 引擎不进入实时伺服环，不参与每个控制周期的计算；
- 真实伺服环只认内核里的控制上下文和总线命令。

### 4. 演示页要求

- 3D 工作台要能看到 `mode AUTO/MANUAL`、`q/q_target`、`err_mm`；
- 模型改动后，页面上的关节轴和内核身体描述要对得上；
- 不能只显示动画，必须显示真实状态。

## 六、G4（支撑能力）：桌面实时控制测试台

桌面测试台不是“QEMU 里能跑就行”，而是要把同一套控制逻辑放到可重复的测试环境里。

### 1. 测试对象

- 同一份控制代码，桌面运行版和控制板镜像共用；
- 桌面端负责 3D 显示、目标下发、状态记录；
- 控制板负责真实采样、控制计算、执行器输出。

### 2. 要测的东西

- 控制周期、实际开始/结束时刻、抖动；
- deadline miss、降级次数；
- 传感器时间戳到执行器命令的端到端延迟；
- 断线、过载、急停、看门狗复位；
- 同一镜像重复启动、重复控制。

### 3. 证据边界

- QEMU 只做功能验收和页面回归；
- TCG 的抖动不能当实时证据；
- 1 kHz 周期、端到端 deadline 必须在目标硬件上测。

### 4. 演示页要求

- 测试台要有一个“运行状态”页面：当前目标、实际状态、误差、周期、miss、降级；
- 测试结束后能导出记录，不靠截图猜。

## 七、G5（横向约束）：每个新功能都要有演示页

这条是硬规则，适用于 G1、G2 和 G3/G4 支撑能力的每一个子功能。

- 新功能必须有唯一按键、页面标题、可观察字段和退出方式；
- 页面必须显示真实内核状态变化，不能只放静态文字；
- 页面矩阵必须新增一行；
- 每次验证都要把已有演示页重新进出一次，确认按键、提示、状态行没有退化；
- 旧演示页坏了，按功能回归处理，先修再做下一项。

没有演示页的功能，视为没做完。

## 八、推进顺序

两条线同时更新，但落地要有顺序，避免互相等待：

1. **先把 G1 的约束和演示页做闭环**：轨迹、限幅、奇异值、deadline 都能在页面上看见。
2. **同时定 G2 拓扑**：单板多臂还是多板组网；拓扑定了再拆 per-robot 上下文。
3. **G3/G4 先打通一条最短闭环**：模型 → 手动目标 → 内核状态 → 3D 显示 → 记录。
4. **再上真实硬件**：驱动/总线、安全状态机、1 kHz 周期、端到端延迟。
5. **每个阶段都跑页面矩阵**：新页面通过，旧页面也不能坏。

## 九、学习顺序

1. 机器人运动学：正运动学、雅可比、奇异值、可操作度；
2. 轨迹生成：三次/五次多项式、S 曲线、jerk 限制；
3. 约束控制：位置/速度/加速度限幅、零空间、阻尼最小二乘；
4. 实时系统：周期、抖动、deadline、优先级反转；
5. 资源核算：定点误差、栈水位、CPU 占用、最坏执行时间；
6. 多机器人：命名空间、上下文隔离、总线路由、故障隔离；
7. 3D 与测试台：模型语义、状态同步、可重复测试、证据导出。

## 十、暂时不做

- 6R 空间臂、四元数姿态、6×N 雅可比；
- 刚体动力学、重力/科氏力、力矩控制；
- 力/位混合控制、传感器融合、视觉伺服；
- 强化学习/学习型控制。

这些放到 G1 验收通过之后，避免一步跨太大。

## 十一、总验收口径

1. 控制算法有页面，能看到真实状态，不是只写日志。
2. 新功能页面通过，旧演示页仍然能进、能退、提示还在。
3. 多机械时，命令和状态都能明确对应到 robot id。
4. 3D 工作台显示的状态和内核状态一致，不是各演各的。
5. 实时性证据来自目标硬件，QEMU 只证明功能正确。
6. 每个阶段都有记录、截图和可重复的启动步骤。
